# MCP OAuth for Nosia connectors

## Goal

Let people authorize remote MCP connectors from Nosia and use those connectors in their chats. Use the MCP client built into RubyLLM instead of the vendored `ruby_llm-mcp` dependency.

## User experience

- For Streamable HTTP connectors, choose between the existing connection settings (no credentials, bearer token, or API key) and OAuth. Existing connectors retain their mode by default. A saved OAuth connector never sends static credentials. OAuth is unavailable for built-in engines, stdio, and legacy HTTP+SSE.
- Saving or adding a connector does not start an MCP or OAuth request. On the connector's details page, **Authorize with OAuth** takes the signed-in member to the provider's consent page. The callback returns to the same account and connector with a localized outcome. Successful consent makes the connector available to this member's chats immediately if it is enabled; a separate connection test is not required.
- For OAuth, show **Authorization required**, **Authorized**, or **Reconnect required** for the current member. Keep the shared enablement setting separate. A member can test their saved connection or browse its capabilities only with their own authorization. One member's consent, connection test, or error does not change another member's status or expose capability results to them.
- **Disconnect** forgets this member's grant in Nosia and stops subsequent uses of it. It does not disable the connector, alter another member's grant, or claim to revoke provider-side consent. An explicit reconnect repeats consent. Saved chat links survive disconnect or temporary unavailability, but they cannot be used until the connector is eligible again.
- Existing legacy HTTP+SSE records remain visible, editable, and deletable without an automatic rewrite. The old transport is no longer available for new records, cannot connect or run tools, and displays a message to obtain a Streamable HTTP URL from the provider. Switching to Streamable HTTP is an explicit edit. Streamable HTTP responses delivered as event streams still work.
- Reuse the current MCP workspace and chat selector with English and French labels and messages. No new catalog entries or provider-specific forms.

## Client and integration boundaries

- Upgrade Nosia's RubyLLM pin from 2.0.0 to 2.2.3 and use `RubyLLM.mcp` through an MCP-specific context for remote connectors. Remove the vendored `ruby_llm-mcp` gem and update the packaging checks that required it. Use the native client's stdio support with the existing deployment opt-in and leave built-in engines on their current local path. Existing working Streamable HTTP endpoints and static authentication continue to use their saved configuration; preserve existing public plain HTTP compatibility only for non-OAuth connectors and document that it is unencrypted.
- Keep transport, discovery, PKCE, dynamic client registration, grant storage, and refresh in RubyLLM. Nosia owns connector configuration, membership checks, authorization lifecycle, and presentation. Use upstream-supported schema changes required to move from RubyLLM 2.0 to 2.2 without replacing Nosia's custom chat models, message broadcasting, or upgrade history. Keep new RubyLLM features out of this scope, including MCP Apps, tasks, and tool questions.
- Use one member-specific grant identity per connector: a Nosia authorization record bound to the connector and its account membership. Pass that record as the RubyLLM OAuth owner. Two connectors at the same URL must still have separate grants, as must the same user in two accounts. Persist pending authorization and tokens via RubyLLM's encrypted `ruby_llm_mcp_credentials` store, with database-backed refresh coordination. Do not duplicate token material in Nosia's application models or browser session.
- Use the same account/member eligibility checks for connector details, connection tests, direct tool execution, and chats. Only enabled and authorized OAuth connectors can be selected or used in chat. Background work resolves the grant from the chat's persisted owner and account, not the ambient session or default account, and checks current membership before each new turn. Never fall back to a shared token or another member's grant. The runtime skips an ineligible connector rather than blocking an otherwise valid conversation. Use distinct tool names in chats for different connectors and keep the existing direct execution API based on the remote tool name and its existing result format.

## OAuth boundaries and failures

- Start consent with a CSRF-protected POST and a top-level browser redirect. Use one stable callback URI derived from Nosia's configured application origin, not the incoming Host header, an arbitrary return URL, or the connector ID. The callback requires a signed-in session and a pending attempt from the same browser session and user. The attempt binds the connector, membership, current configuration identity, RubyLLM-issued state, and the account-scoped return path. A new attempt for the same grant supersedes the previous one. Recheck membership, configuration, and state on return and delegate state, issuer, PKCE, and grant exchange to RubyLLM. Invalid, expired, superseded, or replayed callbacks must not replace a usable grant or connect another user. Do not include authorization data in the post-callback redirect.
- Changing the effective OAuth endpoint or leaving OAuth mode invalidates the old grants and pending attempts. Deleting the connector or removing a membership also removes the affected grant material, including pending attempts; switching back or rejoining never restores an old grant. A name or notes edit does not invalidate authorization. After invalidation, no subsequent request or queued turn uses the old grant.
- Require HTTPS for OAuth and check public outbound destinations at connection time, not just when saving the connector. Apply this to MCP and to every server-side call for OAuth discovery, registration, exchange, and refresh, including hosts named by remote metadata. Connect only to a validated public address while preserving the hostname for TLS verification. Do not follow server-side redirects or let proxies bypass destination checks. Check the browser consent URL for a public HTTPS destination as well.
- Treat denial, expired consent attempts, and a provider that requires a pre-registered app as actionable localized messages. An expired access token is refreshed by RubyLLM. If the provider still rejects the grant after RubyLLM's recovery, mark only that member's grant as requiring reconnection. A transient failure or insufficient scope does not clear the grant or auto-request additional access; report it without vendor response bodies or secrets. Filter OAuth codes, state, URLs containing these values, tokens, and signing material from application logs and document equivalent filtering for reverse proxies.

## Verification

- Write Minitest coverage around the real RubyLLM client with controlled HTTP responses: authorization discovery and dynamic registration, consent with PKCE, valid callback, encrypted persistence across client instances, refresh with token rotation, authenticated tool use, and disconnect.
- Test isolation within and across accounts, duplicate endpoints, changed configuration, deleted membership, revoked grants, malformed or expired callbacks, callback replay, and provider denial. Assert that a chat with unavailable tools can continue and that its background work never borrows a different user's access.
- Test the outbound address policy for both MCP and discovered OAuth destinations, TLS hostname handling, and no secret disclosure in responses or logs. Confirm save and catalog requests never initiate a remote connection.
- Cover the workspace and chat selector in both languages, existing unauthenticated and static-credential Streamable HTTP connectors, stdio opt-in and cleanup, built-in tools, legacy SSE migration messaging, connection-test responses, tool result rendering, and the packaged application boot with no old gem. Run the app's chat, model, and inference regression suites against the new RubyLLM version.

## Out of scope

Pre-registered clients, client metadata documents, client credentials grants, SSO, custom scope or authorization parameter controls, provider-side revocation, a custom legacy SSE transport, and a separate native desktop browser handoff.

## Decisions

- **Use RubyLLM's built-in MCP client and remove `ruby_llm-mcp`.** Keep OAuth discovery, authorization, and token refresh in the upstream client rather than maintaining a separate integration.
- **Each member authorizes separately.** The connector definition remains shared in its Nosia account, but each member authorizes their own access; their chats and background jobs must use only that authorization.
- **Guide migration from legacy HTTP+SSE.** Keep existing records unchanged, stop offering the legacy transport for new connectors, and explain how to switch to a Streamable HTTP endpoint. Do not build a custom transport. This does not remove event-stream responses over Streamable HTTP.
- **Start with dynamic client registration.** Support servers that register the app dynamically; explain when a provider requires a pre-registered app. Do not add client ID/secret settings in this release.
- **Use an explicit OAuth mode, not detection on the first connection test.** Choosing the mode and authorizing access are separate; saving a connector must not contact the remote server.
- **Use RubyLLM for OAuth, with Nosia managing isolation, access, and the workspace flow.** The same member-specific authorization must be enforced in web requests and background jobs, with guarded network access and regression coverage.
