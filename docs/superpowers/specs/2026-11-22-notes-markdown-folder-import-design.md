# Notes: Import a Markdown folder

Date: 2026-11-22

## Decisions

- “Importer des dossiers de notes au format Markdown dans mes notes, par exemple un coffre Obsidian, en reproduisant l’arborescence de dossiers.” Import an existing Markdown collection as editable Notes and reproduce its folder hierarchy.
- “Sélectionner un dossier.” In V1, the browser folder picker is the only way to supply files. Do not add ZIP upload.
- “Oui” to turning Obsidian `[[Note name]]` links into clickable links between notes from the same import. This preserves navigation inside the imported collection.
- “Oui, créer une copie séparée.” Every deliberate import creates a separate root folder. When a sibling already has the chosen name, use the first available numbered suffix, such as `Mon coffre (2)`. Never merge or overwrite existing folders or notes.
- “Oui” to the V1 flow: review the account and counts, run the import in the background, and open the new branch with a summary. The imported notes share the same visibility and indexing behavior as existing Notes.

## User flow

- Offer “Import a Markdown folder” in Notes to current account members who can create notes. Let them select a folder in the browser. If folder selection is unsupported, explain that it requires a compatible browser; do not offer a flat file picker that loses the paths.
- Before uploading, show the target account, the selected root name, and the note, folder and ignored-file counts. Explain that the import will create a separate branch at the account root, that the result will be shared with account members, and that saved content is indexed by the configured provider, which can be remote.
- After confirmation, show upload and import status, then open the new root folder with the result: actual folder name, server-confirmed note and folder counts, ignored-file counts by reason, and unresolved-link counts with up to 100 examples. The two ignored-file counts (Obsidian configuration and other non-Markdown files) come from the browser selection and are labeled as such; Nosia does not list or upload those files. Errors tell the user what to fix and how to select the folder again. Import success means the notes have been saved; indexing may still be pending.

## Files, hierarchy, and links

- Recreate the selected root and every subfolder containing imported Markdown, directly or through a descendant. Native folder selection does not provide empty directories. Import `.md` (case-insensitive); ignore Obsidian’s `.obsidian` directory and files other than Markdown. Do not upload ignored files. No attachments, ZIP upload, vault synchronization, or plugin support.
- Use the filename stem as the title. Convert supported Markdown to editable rich text with the existing Commonmarker and Notes sanitization pipeline. Preserve front matter as a readable code block without converting Obsidian properties to Notes fields. Use normal Notes hashtag, text search, and indexing behavior; the importer never fetches embedded media or external resources.
- Resolve Obsidian `[[Note]]`, `[[Folder/Note]]`, and `[[Note|Label]]` only inside the current import. Bare names match a unique filename stem; qualified paths start at the selected root. A trailing `.md` is optional for wikilinks and matches case-insensitively. Compare other path components case-sensitively after Unicode NFC normalization. Wikilink paths are literal and are not URL-decoded.
- Resolve a Markdown link to a `.md` file relative to the note containing the link. Decode percent escapes once per segment, leave `+` literal, and reject malformed escapes or decoded path separators. Relative `.` and `..` are allowed in link targets only if resolution stays inside the imported root; those components are not accepted in uploaded paths. Use ordinary Notes URLs so a later move does not break the link. Keep valid external hyperlinks and never rewrite code spans or code blocks.
- Leave missing, ambiguous and heading/block-specific references as readable, non-clickable text, retaining their label and target. Report their source and original target without guessing. Render Obsidian embeds such as `![[diagram.png]]` as readable, non-clickable references, not attachments; HTML and Markdown media must never cause a network fetch.

## Upload and lifecycle

- Confirmation starts one account-scoped upload, with a server-validated manifest of relative Markdown paths and byte lengths. A per-confirmation key scoped to the account and initiator makes starting the same upload retry-safe. Upload batches against that manifest; a repeated file is a no-op only if the path and content digest match. A finalize request verifies that the complete manifest arrived and seals it before queueing processing. A repeated finalize returns the same import status. Missing files prevent sealing; new or changed files cannot be added once sealed.
- Only the initiator who is still an account member can stage or seal files and view the import status and report. Store Markdown privately in staging accessible by both web and job processes; never expose staged files via public download URLs. Job arguments contain the import identifier, not the upload content. Do not put note contents in logs or error messages.
- Once finalized, the import moves through queued and running to success or failure. A periodic reconciler runs every five minutes. It retries enqueueing sealed imports with no recorded enqueue using the same import ID; a duplicate delivery cannot claim an import already being processed. After 24 hours without a start, expire uploads still unsealed and fail sealed or queued imports that never acquired a worker claim.
- A running worker holds a renewable 15-minute claim, checked before opening staged files and inside the publication transaction. A worker renews it while preparing the import. On expiry, the reconciler revokes the claim and marks the import failed under the import lock; a late worker may no longer open files or publish. Keep staging for valid queued or running imports. Remove staging after the import reaches a terminal state. Cleanup failures are retried separately and cannot change the import result.

## Validation and publication

- Treat submitted paths and content as untrusted. Validate the root and all relative paths, normalize to Unicode NFC, and reject absolute paths, traversal, empty components, control characters, malformed names, and duplicate normalized paths. Use paths as logical names, never filesystem destinations. Require UTF-8 Markdown.
- Document and enforce server-side launch limits: 500 Markdown files, 250 folders including the root, 32 subfolder levels, 2 MiB per file, 32 MiB total, 255 UTF-8 bytes per path component, and 1,024 bytes per path. Cap rendered content at 4 MiB per note and 64 MiB total. Limit each multipart request to 16 files and 4 MiB including overhead (or the deployment limit if lower); cap the manifest at 1 MiB without increasing global upload limits. Validate the two ignored counts as nonnegative 32-bit integers. Reports include at most 100 examples, each with a bounded path and an excerpt of at most 512 UTF-8 bytes from the original target.
- Prepare Markdown conversion and resolve links to logical paths outside the account write lock. Under the same lock used by Notes writes and membership revocation, recheck the initiator’s membership and whether this import has already published. Reserve a nonconflicting root name, including names of trashed roots; if a suffix exceeds the name limit, shorten the stem at a character boundary. Preallocate the entire batch’s server-owned note IDs from the Notes primary-key sequence before filling in the final link URLs. Pass those IDs through an internal first-save entry point that uses the existing content pipeline (sanitization, text, tags and revision). Do not accept IDs from the browser or save intermediate bodies.
- Publish the full folder tree, all final notes, and the successful import result in one transaction. During publication, hold the import lock after taking the account lock so the reconciler cannot revoke the worker midway through the transaction. A blocking failure, including an empty import or revoked membership, leaves no partial branch. Normal indexing runs after commit; indexing failures remain note indexing failures, not import failures. Retries of the same import reuse the saved result; a second deliberate import creates another copy.

## Verification

- Import a nested fixture vault twice; verify independent roots, preserved hierarchy, sanitized formatting, and localized reports. Cover forward, mutual, and self-links, aliases, parent-relative and percent-encoded Markdown links, ambiguity, and unsupported embeds. Open converted links and confirm they survive a subsequent Lexxy edit.
- Verify cancellation before upload, unsupported picker guidance, sealed file set and retry-safe batches/finalization, status and final navigation, bounded reports, malformed paths, empty/oversized uploads, rollback, duplicate job delivery, membership revocation and cross-account status access. Simulate a crash between seal and enqueue and a worker death after claim; verify recovery or terminal failure with cleanup, and assert that an expired worker cannot publish. Confirm that Notes search and indexing use the final saved notes and that no indexing job runs for a rolled-back import.
- Exercise a synthetic import at the launch limits. Measure account-lock duration and index queue growth and confirm a normal Notes write made during preparation does not wait for Markdown conversion. If the caps do not let ordinary writes and indexing remain responsive, lower the caps before shipping.
